# Tests that pin a contract the compiler cannot see

`ymck_decode_test.cpp` is the reference example for a whole class of bugs in
this project: a decoder's output is only correct relative to a convention that
lives **outside the repository** (a file format, a library, a device). Reading
the source cannot settle it - every wrong variant is internally consistent.

The CMYK plane polarity is the case that cost us three releases-in-a-row:
F-M23, ec8032f and 9746da5 each re-derived the assumption from the previous
patch, and the last one turned every real Photoshop file black while all of our
own samples still "passed". The samples were generated from the same assumption
as the code, so they could only prove self-consistency.

## The pattern

When a value's meaning cannot be derived from the code, do not document it -
**pin it and make the pin fail loudly**:

1. **One named constant.** `YmckDecode::kPlaneIsInverted` is the only place
   that knows whether a channel byte is ink or light. Two flags in two files
   is how the branches drifted apart.
2. **Endpoint assertions, not sample comparisons.** `no ink => white`,
   `full ink => black`, `more K => darker`, `full C => (0,255,255)`. These are
   statements about the picture, so they stay true regardless of how the code
   is written. A comparison against a generated sample only proves the
   generator agrees with the decoder.
3. **One conversion site, enforced.** `InvertPlaneInPlace()` is called exactly
   once, and `check_ymck_polarity.py` fails the build if the subtraction shows
   up anywhere else, or if the call disappears or doubles.
4. **A switch that makes the fallback reachable.** A branch that never executes
   cannot be tested - F-M23 "fixed" one and verified nothing.
   `JPEGVIEW_DISABLE_CMYK_ICC=1` forces `CreateTransform()` to fail for CMYK so
   the no-profile paths really run. The switch only exists in debug builds
   (`#ifndef NDEBUG`); a Release build ignores the variable.

## Running it

No Windows toolchain needed - the header is plain C++17:

```sh
g++ -std=c++17 -Wall -Wextra -O2 -I src/JPEGView tests/ymck_decode_test.cpp -o /tmp/ymck_test
/tmp/ymck_test
python3 .github/scripts/check_ymck_polarity.py
```

CI runs exactly these three commands plus a fourth step that proves the guard
can fail.

## Proving the guard has teeth

A test that has never failed is not evidence. Two historical regressions are
reproducible in one line each, and both must be rejected at compile time:

```sh
# 9746da5: the plane is never inverted
g++ -std=c++17 -DYMCK_PLANE_IS_INVERTED=0 -I src/JPEGView tests/ymck_decode_test.cpp -o /tmp/m1
#   -> error: static assertion failed: A1: a plane byte of 255 must be no ink...

# ec8032f: the naive formula inverts a second time (edit a copy of the header,
# replace (255u - inkA) * (255u - inkB) with inkA * inkB)
#   -> error: static assertion failed: A1 ... A2 ... A3 ... A4
```

The static gate has the same property: deleting the `InvertPlaneInPlace` call
reports `found 0`, duplicating it reports `found 2`, and re-inlining
`255 - p[0]` reports a per-channel inversion. All three were exercised before
this file was committed.

## CMYK pixel test (B-CMYK1)

`tests/cmyk_pixel_test.cpp` is the end-to-end counterpart to the YMCK
endpoint test: it reads real CMYK files and asserts the picture, not just
the arithmetic. The samples are two 6x1 strips with known ink values
(`tests/samples/cmyk_chart_6x1.psd` and `.jpx`, generated by
`tests/samples/make_cmyk_samples.py`): white, black, cyan, magenta,
yellow and a mid-grey K=128 patch that pins the rounding. Expected RGB
values are the naive ink formula evaluated by hand.

The decode step is split by format because the product decoders are
MFC-coupled and do not compile on Linux:

- PSD: a minimal reader in the test (uncompressed 8-bit 4-channel CMYK
  PSD only) mirrors the product's channel permutation and single
  inversion, then runs the product's own `YmckDecode.h` conversion.
- JP2: decoded with the system OpenJPEG (`libopenjp2`), then the
  product's `YmckDecode::InkToRgb` with no inversion. Note the OpenJPEG
  quirk: `color_space` is still UNSPECIFIED after `opj_read_header` and
  only becomes CMYK after `opj_decode`, so the test asserts it after
  decode.

`tests/cmyk_reference_check.py` is an independent cross-check: it
decodes both samples with Pillow and the system OpenJPEG tools and
asserts the same picture. It shares no code with the C++ test.

```sh
g++ -std=c++17 -Wall -Wextra -O2 -I src/JPEGView tests/cmyk_pixel_test.cpp \
    -o /tmp/cmyk_pixel_test $(pkg-config --cflags --libs libopenjp2)
/tmp/cmyk_pixel_test
python3 tests/cmyk_reference_check.py
```

CI runs both. The product PSD/JP2 wrappers themselves and the ICC
profile paths are not covered here (they need MFC/lcms2) and still need
a Windows device test against these same two files.

## Loader regression tests (B-TEST1)

The loader fixes the release notes call "covered by a regression case"
now have cases in the repo. The decoders themselves are MFC-coupled and
do not compile on Linux, so the testable logic was moved into plain
headers that both the product and the test include:

- PNM scaling: `src/JPEGView/PnmScale.h` holds the one scaling function
  (`PnmScale::ScaleSamples`, moved verbatim out of `PPMWrapper.cpp`).
  `tests/loader_pnm_test.cpp` decodes hand-written PNM samples with the
  vendored stb_image and asserts the scaled pixels (8-bit maxval=15
  white to 255, 16-bit maxval=4095 white to 255, maxval=255/65535
  identity). `tests/check_pnm_scale.py` is the static gate: the
  arithmetic lives only in `PnmScale.h`, and `PPMWrapper.cpp` must call
  it exactly once and hold no second copy.
- JPEG Exif APP1: `src/JPEGView/FindEXIFBlock.h` holds the segment walk
  (moved verbatim out of `Helpers.cpp`; only `uint8` became
  `unsigned char`, the same type). `tests/loader_jpeg_exif_test.cpp`
  runs it over hand-written JPEG samples: Exif APP1 first, XMP APP1 in
  front of Exif (still found), over-short "Exif" APP1 (rejected), and
  no-Exif files (NULL).
- TGA 15-bit RLE: the RLE decoder is embedded in `ReaderTGA.cpp` and
  cannot be extracted, so there is no C++ test for it.
  `tests/check_tga_rle_sample.py` is sample + reference validation only:
  it decodes the hand-written 15-bit RLE samples per the TGA spec and
  asserts the pixels. Decoding them through the real loader still needs
  a Windows device test.

```sh
g++ -std=c++17 -Wall -Wextra -O2 -I src/JPEGView tests/loader_pnm_test.cpp -o /tmp/loader_pnm_test
/tmp/loader_pnm_test
g++ -std=c++17 -Wall -Wextra -O2 -I src/JPEGView tests/loader_jpeg_exif_test.cpp -o /tmp/loader_jpeg_exif_test
/tmp/loader_jpeg_exif_test
python3 tests/check_pnm_scale.py
python3 tests/check_tga_rle_sample.py
```

CI runs all four. Samples live in `tests/samples/` (`pnm_*`, `jpeg_*`,
`tga15_*`); each is a hand-written minimal file, and its expected
pixels are stated in the test that reads it.

## OCR joining mirror (#84)

The OCR word-joining logic (`SelectedText`, `NeedsSpaceBetween`,
`SplitInsideLatinWord`, `PunctJoinsWithoutSpace`, `MergeEngineLines` in
`src/JPEGView/OcrEngine.cpp`) is Windows-only (WinRT), so it cannot be
compiled on Linux. `tests/check_ocr_84_mirror.py` is a Python mirror of
exactly that logic, run over the two real samples in `tests/samples/`:

- `ocr_ko_words.png` (1500x560, Malgun Gothic 72px): four Korean lines.
  Before the fix the mirror joins them without spaces
  ("안녕하세요세계"); after, the spaces are kept ("안녕하세요 세계").
- `ocr_vertical_zh.png` (980x720, SimSun 96px, 3 columns x 5 chars):
  the three columns share one vertical centre, so the old sort
  degenerates to left-first and the order comes out reversed
  ("夜来风雨声" first); after, the right column comes first
  ("春眠不觉晓" first).

The mirror measures the word/column boxes from the images themselves
(projection analysis) and asserts the before/after text for both
samples, plus the vertical-gap direction for the Latin-word check and
the Chinese/Japanese no-space regression. It verifies the joining
logic only; the WinRT recognition itself (whether vertical text comes
back as one column per line) still needs a Windows device test on
these same two files.

```sh
python3 tests/check_ocr_84_mirror.py
```

## Adding the next one

If you are about to rely on a convention that is not visible in the source
(a TIFF orientation flag, a JPEG restart interval, a device gamma, an EXIF
unit), do this instead of writing a comment:

- put the convention in one named constant with a comment naming the **proof**,
  not the belief ("renders correctly on build 19897de" is a proof; "PSD stores
  ink" is a belief);
- write four assertions that a wrong answer cannot satisfy, and check them
  against a real artefact produced by the original tool, never against your own
  generator;
- add a static gate if a second copy of the arithmetic would break it;
- add a switch if the code path is otherwise unreachable.
